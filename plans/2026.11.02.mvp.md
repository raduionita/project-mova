## 1. 🏁 Release definition

Mova 1.0.0 is release-ready when all of the following are true:

1. A new user can complete the expanded onboarding (units, gender, birth date, weight, height, goals, experience, schedule, notification choice), receive a plan, finish a workout, see a summary, and find that workout in Progress after restarting the app.
2. The live logger supports previous values, set completion, rest timer, pause, resume, discard protection, and recovery after process death.
3. Progress shows honest local metrics: total workouts, total volume, streak, weekly volume, PRs, history, and a beta strength score.
4. Train supports search, filters, exercise details, routine creation, editing, reordering, and starting a routine.
5. Social supports a local feed, sample posts, own workout posts, kudos, and PR share cards.
6. Me supports profile editing, body weight, unit preferences, reminders, health status with a manual fallback, privacy, legal links, and local data reset.
7. All empty, loading, error, denied-permission, and corrupt-data states are handled without a crash.
8. The design system is applied through tokens. No screen hardcodes colors, type sizes, radii, or spacing.
9. `flutter analyze` reports zero issues.

12. Release assets exist: app name, icon, splash, version, privacy text, terms text, open-source licenses, and store metadata drafts.
13. Accessibility checks pass at 1.3x text scale with VoiceOver and TalkBack on the core loop.
14. No `TODO` or `FIXME` remains in `lib/`.
15. No em dash appears in `lib/`, `test/`, or user-facing assets.

## 3. Architecture

### 3.1 Layers

```text
Screens and widgets
        |
        v
Providers (ChangeNotifier)
        |
        v
Services (domain and platform)
        |
        v
StorageService (shared_preferences)
```

Rules:

- Widgets read state from providers and call provider commands. They do not read storage directly.
- Providers own state transitions and call services. They never import Flutter widgets.
- Services contain domain logic and platform adapters. They never import widgets.
- `StorageService` is the only class that touches `shared_preferences`.
- Models are immutable, with `copyWith`, `fromJson`, and `toJson`.
- Cross-provider coordination happens in a thin `AppCoordinator` or inside the provider that owns the transaction. Avoid provider-to-provider cycles.
- A single `Clock` abstraction provides time. `SystemClock` is the production implementation. Tests inject `FakeClock`.
- An `IdService` wraps UUID generation. Tests can inject a deterministic sequence.

### 3.3 Startup sequence

1. `WidgetsFlutterBinding.ensureInitialized`.
2. Initialize `SharedPreferences`.
3. Build `StorageService`, `Clock`, `IdService`, and seed service.
4. Read the profile, settings, plan, active session, workouts, routines, PRs, and social posts.
5. Validate schema versions and discard corrupt payloads individually.
6. Seed the exercise library if absent.
7. Seed sample social posts if absent and not dismissed.
8. Load notifications and health services lazily.
9. Build providers in the order defined in section 3.6.
10. Route to `/welcome` if onboarding is incomplete. If an onboarding draft exists, resume at the saved step. If an active session exists, open `/logger`. If a paused session exists, open `/today` with a Resume workout action. Otherwise open `/today`.
11. Remove the native splash after the first frame.

The startup gate is a dedicated widget that shows the branded splash until initialization finishes. It must never show a blank screen.

### 3.6 Provider build order

Build providers in this order. A provider may read storage or a service, but must not import another provider's concrete class.

| Order | Provider | Depends on |
|---|---|---|
| 1 | `SettingsProvider` | `StorageService` |
| 2 | `ProfileProvider` | `StorageService` |
| 3 | `ExerciseProvider` | `StorageService`, `SeedDataService` |
| 4 | `RoutineProvider` | `StorageService`, `ExerciseProvider` data |
| 5 | `PlanProvider` | `ProfileProvider` and `SettingsProvider` data |
| 6 | `OnboardingProvider` | `StorageService` |
| 7 | `WorkoutProvider` | `PlanProvider`, `RoutineProvider`, `ExerciseProvider` data |
| 8 | `HistoryProvider` | `StorageService` |
| 9 | `ProgressProvider` | `HistoryProvider`, `ProfileProvider` data |
| 10 | `SocialProvider` | `HistoryProvider`, `SettingsProvider` data |
| 11 | `AppCoordinator` | All providers |

When a provider needs another provider's data, pass the data or a callback from `app.dart` instead of importing the other provider.

### 3.4 Error handling

- Storage failures never crash startup. Log, use a safe default, and show a dismissible banner on Today.
- A corrupt single payload is dropped without touching other keys.
- Domain validation failures return a `Result` and surface a snackbar.
- Platform integrations fail soft: health becomes unavailable, notifications become off, sharing falls back to a save dialog.
- No silent catch blocks. Every catch either recovers or reports.

**Failure and side-effect rules**

- Storage reads return null for missing, corrupt, or future-schema data. Writes return false on failure. Neither throws to the UI.
- Platform adapters return unavailable or denied instead of throwing.
- Plan generation returns the fallback plan on failure.
- Providers keep the last good state, set `error`, and clear `isLoading` in `finally`.
- Side effects are limited to the storage keys in section 6.2 and the platform permission prompts named above.
- Every provider persists only through the storage keys in section 6.2.

- At most one session is active or paused.

- A plan always has between 1 and 7 training days and at least one exercise per training day.
- A routine has between 1 and 20 exercises.
- PRs are recomputed from history after any delete.
- Unit conversion happens only at display and input boundaries. Storage stays metric.
- IDs are UUID v4 and never reused.
- A completed profile has non-null gender, birthDate, at least one goal, and experienceLevel.
- The first selected goal is the primary goal for plan generation.
- Weight and height may be 0, meaning unknown.
- A birth date must be at least 13 years before today and no more than 120 years before today.
- The onboarding draft current step must be one of the 11 defined steps.
- Unit preferences affect display only; storage remains kg, cm, and km.

## 7. Domain rules

### 7.1 Unit conversion

- Store kilograms, centimeters, kilometers, and seconds.
- `kg -> lb`: multiply by `2.2046226218`, round to 1 decimal for display.
- `lb -> kg`: divide by `2.2046226218`, round to 0.5 kg on input.
- `cm -> in`: divide by `2.54`, round to 1 decimal for display.
- `in -> cm`: multiply by `2.54`, round to 1 cm on input.
- `km -> mi`: multiply by `0.6213711922`, round to 1 decimal for display.
- `mi -> km`: divide by `0.6213711922`, round to 0.1 km on input.
- Step and rep values are integers.
- Strength score always uses kg.
- A unit switch changes labels and displayed values immediately, without mutating stored data.
- Onboarding defaults to kg, km, and cm. The unit selection screen can change each independently.
- The distance unit is stored for future distance features. No distance input ships in v1.

### 7.2 Workout calculations

```text
setVolumeKg = weightKg * reps
sessionVolumeKg = sum of setVolumeKg for completed sets with external load
sessionSets = count of completed working sets
sessionDuration = completedAt - startedAt, minus paused time
```

- Warm-up sets are excluded from volume and PRs.
- Bodyweight sets add reps and sets but zero volume.
- Duration is clamped to zero if the clock moves backward.
- A session with no completed sets can still be saved, with zero volume and no PR.

### 7.3 Estimated 1RM and PRs

```text
e1RM = weightKg * (1 + reps / 30)   for reps 1 to 12
```

- Above 12 reps, compare the best weight and reps set, not an estimate.
- Only completed working sets count.
- A new PR requires a value strictly greater than the stored best.
- Store `previousBestKg` at detection time.
- One PR record per exercise per session.
- Recompute all PRs after history deletion.

### 7.4 Streak

- Group completed sessions by local `dateKey`.
- A walk session counts.
- Consecutive days ending today or yesterday count as the current streak. If the last activity is older than yesterday, the streak is zero.
- The streak never exceeds days since profile creation.
- Recompute from history. Do not persist a counter.

### 7.5 Strength score

```text
score = round(
  sum((bestE1rmKg / bodyWeightKg) * 100 for tracked lifts)
  / trackedLiftCount
)
```

- Tracked lifts: squat, bench press, deadlift, overhead press.
- Require at least three completed sessions, at least two tracked lifts, and a body weight greater than zero.
- Label beta. Provide an explanation sheet.
- Show no ranking and no percentile.
- Show the weekly delta only when a prior score exists.

### 7.6 Plan generation

Inputs: goals, experience level, days per week, selected weekdays, default session duration 55 minutes, full-gym equipment. The first selected goal is the primary goal and drives the prescription. Additional goals are stored and displayed but do not change the week 1 template.

Split templates:

| Days | Split |
|---|---|
| 1 | Full Body |
| 2 | Full Body A / Full Body B |
| 3 | Push / Pull / Legs |
| 4 | Upper / Lower / Upper / Lower |
| 5 | Push / Pull / Legs / Upper / Lower |
| 6 | Push / Pull / Legs / Push / Pull / Legs |
| 7 | Six training days plus one active recovery day |

Goal prescription:

| Goal | Sets | Reps | Rest |
|---|---|---|---|
| Build muscle | 3 to 4 | 8 to 12 | 60 to 90 s |
| Get stronger | 4 to 5 | 3 to 6 | 120 to 180 s |
| Lose weight | 3 | 12 to 15 | 45 to 60 s |
| Stay healthy | 2 to 3 | 10 to 15 | 60 s |

Experience modifiers:

- Beginner: subtract one set per exercise, prefer machines and dumbbells.
- Regular: baseline prescription.
- Gym rat: add one set to the first compound per day.
- Veteran: add one set and prefer free-weight compounds.

Selection rules:

- The primary goal is `goals.first`. If goals is empty, use `buildMuscle` and record a warning.
- Deterministic for the same profile seed and week.
- Compound movements first, isolation last.
- No duplicate exercise in the same day.
- 5 to 7 exercises per training day, adjusted by estimated duration.
- Each day includes the target muscle groups for its split.
- Unselected weekdays are rest days.
- Regenerating a plan never deletes history.
- Plan editing moves a whole split day to another weekday. It never moves individual exercises.
- Moving a day onto an occupied weekday swaps the two days. Moving onto a rest day leaves the old weekday as rest.
- The plan preview can return to schedule before confirmation; the generated plan is replaced.

### 7.7 Progression

MVP progression is suggestion only:

- Prefill the last completed weight and reps for the same exercise.
- If every working set in the previous session reached the top of the rep range, suggest `+2.5 kg` for upper body and `+5 kg` for lower body.
- Show the suggestion as a target hint. Never auto-change logged values.
- No periodization, deload, or RPE programming in v1.

### 8.1 Onboarding flow

The onboarding flow has 11 screens. Welcome is the entry screen; the progress indicator covers the 10 onboarding steps after Welcome.

1. Welcome: app promise and Get started. If a draft exists, Continue resumes at the saved screen.
2. Units: weight kg or lb, distance km or mi, body cm or in. Defaults are kg, km, cm. All three selections persist before Continue. Distance is saved for future cardio tracking; no distance entry ships in v1.
3. Gender: three full-width buttons with icon and text for male, female, and other. Selection is required.
4. Birth date: three vertical wheels for month, day, and year. Default is 25 years before today. The date must make the user at least 13 and no more than 120 years old. Leap years are handled.
5. Weight: horizontal ruler slider. Range is 30 to 250 kg, step 0.5 kg. The displayed value uses the weight unit. The stored value is kg. Skip stores 0.
6. Height: vertical roller. Range is 120 to 230 cm, step 1 cm. The displayed value uses the body unit. The stored value is cm. Skip stores 0.
7. Goals: multi-select cards for build muscle, get stronger, lose weight, and stay healthy. At least one is required. The first selected goal is primary and is shown as such.
8. Experience: single-select cards for beginner, regular, gym rat, and veteran, each with a one-line description.
9. Schedule: days per week from 1 to 7 and the training weekdays. Default is 3 days on Monday, Wednesday, and Friday. At least one weekday is required and the count must match daysPerWeek.
10. Notifications: explain workout reminders. Enable asks for system permission. Deny, Not now, or unavailable continues with reminders off. The choice is stored and can be changed later in Settings.
11. Plan preview: shows the generated week. Confirm persists profile, settings, and plan through `AppCoordinator`, clears the draft, and opens Today. Edit schedule returns to step 9 with values preserved. If generation used the fallback, the plan is labeled Starter plan.

Every step persists the draft before moving forward. Back preserves values. Killing the app and reopening resumes at the saved step. Weight, height, and notifications can be skipped; gender, birth date, goals, experience, and schedule are required. The flow is usable at 1.3x text scale and exposes wheel and slider values to screen readers.

## 14. ⚠️ Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Health permissions and store declarations delay release | High | Ship manual steps fallback first. Treat native health as optional at runtime. Prepare Play Console declaration early |
| Phase-aware shell leaves dead tabs or dead actions | High | The tab registry is built from the highest completed phase; Today hides steps, reminders, and actions until their phase lands; the Phase 2 gate verifies hidden states |
| Legal and help links become dead ends | Medium | `SET-19` implements legal and license screens; QA O verifies every Settings link |
| Notification timing on Android | Medium | Use inexact scheduling. Do not promise exact delivery in copy |
| Background timer drift | Medium | Compute elapsed time from wall clock, not a tick counter |
| Share card memory or layout overflow | Medium | Render offscreen at fixed logical size, test on small devices, cap image to 1080x1920 |
| Local data loss | High | Write completed sets immediately, keep active session separate, validate schema, test reset |
| Scope creep from social features | High | Keep Social local and kudos-only. No friends, comments, or leaderboards |
| Onboarding length causes drop-off | High | Show progress, allow weight, height, and notifications to be skipped, resume the draft, keep each step to one decision |
| Custom wheel and ruler controls are hard to use with assistive technology | Medium | Expose semantic labels and values, support drag and keyboard alternatives, test at 1.3x text scale |
| Gender and birth date collection raises privacy concerns | Medium | Explain local-only storage, provide Other, keep data on device, disclose in privacy text |
| Dense logger layout at 1.3x text | Medium | Flexible rows, minimum heights, test on 360x640 |
| Test flakiness from timers | Medium | Inject clock and timer fakes. Avoid real waits |
| Web feature gaps | Low | Feature-detect and degrade. Web is not the primary release |
| Store credentials unavailable | High | Mark as manual blocker. Build and test with debug signing meanwhile |
| Emoji and font rendering differences | Low | Bundle fonts. Emoji only in onboarding and social |
| Overusing lime | Low | Enforce one primary action and token rules in review |
| Notification desugaring or receiver misconfiguration | Medium | Follow the package setup, smoke test Android 13 and 14, keep reminders off on failure |
| iPad share sheet needs an anchor | Medium | Pass `sharePositionOrigin` from the share button rect and test on iPad |
| Web localStorage quota | Low | Catch write failures, show a storage warning, keep the session in memory |
| OS backup undermines the local-only claim | Medium | Disable Android backup and document iOS backup behavior in the privacy text |
| Native plugin API changes during the build | Low | Lock versions, upgrade only for release blockers, rerun gates |
