## 1. 🎯 Scope

This plan adds three related training-intelligence features:

1. **Progressive overload assistant**
   - Prefill working sets from the last completed performance for the same exercise.
   - Add 2.5 kg (or 5 lb) when every completed working set reached the top of the current rep range.
   - Keep the same weight when the top was not reached.
   - Show a short, honest reason in the logger.
   - Apply when starting a plan day, starting a routine, and adding an exercise.

2. **Equipment-aware plans and substitution**
   - Let the user select available equipment during onboarding and from Settings.
   - Generate plans only from compatible exercises.
   - Skip unavailable muscle groups with a visible warning instead of crashing or silently filling the week with unusable exercises.
   - Let the user swap the current exercise in the logger for another compatible exercise from the same muscle group.

3. **Plate calculator**
   - Calculate plates per side for a target barbell weight.
   - Support kg and lb plate loadouts.
   - Show the closest loadable weight and the remainder when the target is not exact.
   - Open from the live logger without changing logged data.

### Non-goals

- No RPE, tempo, percentage-based programming, deload weeks, or periodization.
- No external AI service, account, cloud sync, or remote exercise library.
- No per-gym plate inventory. The calculator assumes one standard loadout per unit.
- No custom equipment names or custom plate weights.
- No automatic exercise swapping without user confirmation.
- No changes to social accounts, leaderboards, shared routines, or coach features.
- No routine-builder equipment filtering. Manual routines remain user-controlled.
- No equipment-aware exercise detail recommendations outside the swap picker.

## 3. 🧠 Domain definitions

### 3.1 Equipment groups

Add `EquipmentGroup` as the user-facing selection. The exercise library keeps its existing string equipment values.

| Group | Label | Description | Exercise equipment values |
|---|---|---|---|
| `bodyweight` | Bodyweight | No equipment needed | `Bodyweight` |
| `dumbbells` | Dumbbells | Fixed or adjustable dumbbells | `Dumbbell` |
| `barbell` | Barbell and EZ bar | Barbell, rack, and EZ bar | `Barbell`, `EZ Bar` |
| `machines` | Machines | Selectorized and plate-loaded machines | `Machine` |
| `cables` | Cable station | Pulleys and cable stacks | `Cable` |
| `kettlebells` | Kettlebells | One or more kettlebells | `Kettlebell` |
| `accessories` | Accessories | Ab wheel, medicine ball, and sled | `Ab Wheel`, `Medicine Ball`, `Sled` |

Rules:

- The default selection is every group.
- At least one group is required in onboarding and Settings. Continue or Save stays disabled when none is selected.
- `EquipmentGroup.expand` returns the set of exercise equipment strings.
- Unknown stored group names are ignored.
- A missing or empty stored list falls back to every group for backward compatibility.
- The profile is the source of truth for the current selection. A generated `TrainingPlan` records the selection it was generated with.
- Existing users with no equipment field keep full-gym behavior until they change it.

### 3.2 Plan generation

`PlanGeneratorService.generate` gains an optional `availableEquipment` list. When omitted, it uses every group.

Order of operations for every muscle pool:

1. Expand selected groups to allowed exercise equipment strings.
2. Filter the library to exercises whose `equipment` value is allowed.
3. Apply the existing experience-based equipment ranking, compound preference, and deterministic rotation.
4. If a muscle has no eligible exercise, skip it and add the muscle to a warning list.
5. If a day ends with fewer than three exercises, fill from other allowed exercises using the existing ranking.
6. If the whole plan would be empty, build the existing fallback body plan from allowed exercises and mark `isFallback`.
7. Append a human-readable sentence to `lastWarning` for every skipped muscle group.

Acceptance rules:

- Full-gym exercise selection and prescriptions remain identical to the current generator output for the same inputs and clock. The serialized plan now also records the equipment list.
- Dumbbell-only generation never includes barbell, machine, cable, kettlebell, or accessory equipment unless the user selected a group that maps to it.
- Bodyweight-only generation never crashes when Biceps or Forearms have no matching exercises.
- The plan stores the equipment list used to generate it.
- Regenerating from plan overview uses the profile's current equipment, not the old plan's equipment.

### 3.3 Progressive overload

Add a deterministic `ProgressionService` and a serializable `ProgressionSuggestion`.

A suggestion is produced only when:

- The exercise has at least one completed, non-warmup set in history.
- The most recent qualifying set has `weightKg > 0`.
- The exercise equipment is not `Bodyweight`.

Reference workout:

1. Scan history newest first.
2. Choose the first workout that contains at least one completed, non-warmup set for the exercise.
3. Use every completed, non-warmup set for that exercise in that workout.
4. Choose the reference set by highest weight, then highest reps, then highest index.

Decision:

- `topReached` is true when every completed working set has `reps >= targetRepsHigh`.
- Loaded and `topReached`: suggested weight is `reference.weightKg + incrementKg`.
- Loaded and not `topReached`: suggested weight is `reference.weightKg`.
- Suggested reps are `targetRepsLow`.
- Clamp suggested weight to `500 kg`.
- Ignore incomplete sets, warmup sets, and deleted workouts.
- Do not scan further back when the newest qualifying workout does not reach the top. Repeat its weight.

Increments:

- kg mode: `2.5 kg`.
- lb mode: `5 lb` converted to kg before addition.
- The increment is computed once in `AppCoordinator` from the current weight unit and passed to the service.

Suggestion model fields:

- `exerciseId`
- `weightKg`
- `reps`
- `previousWeightKg`
- `previousReps`
- `action` (`repeat` or `increase`)
- `sourceWorkoutId`
- `sourceSetId`

Application:

- `WorkoutProvider.startFromPlanDay`, `startFromRoutine`, and `addExercise` accept an optional suggestion map or suggestion.
- New working sets use the suggested weight and rep target.
- The suggestion is persisted on `SessionExercise.progression` so the logger can explain why the weight was prefilled.
- Existing sessions with no field parse as `null`.
- Edits to a set do not rewrite the stored suggestion.

### 3.4 Exercise substitution

Substitution happens in the live logger.

- Entry: a 32x32 swap icon with tooltip `Swap exercise` beside the current exercise title.
- Picker filters:
  - same primary muscle by default,
  - selected equipment only,
  - current exercise excluded.
- If no same-muscle alternatives exist, show all compatible exercises and a helper line explaining the fallback.
- If any set is completed, show a confirmation dialog that explains the logged sets will reset.
- Confirm replaces the exercise at the same order and preserves the set count.
- Every set becomes uncompleted with weight `0`, the existing rep value, and no progression hint.
- Cancel changes nothing.
- The active session is saved with the replacement.
- History, PRs, and other exercises are untouched.

### 3.5 Plate calculator

Add a unit-agnostic calculator with two standard loadouts.

| Unit | Bar choices | Plate pairs available |
|---|---|---|
| kg | 20, 15, 10 kg | 25, 20, 15, 10, 5, 2.5, 1.25 kg |
| lb | 45, 35, 25 lb | 45, 35, 25, 10, 5, 2.5 lb |

Rules:

- Plates are unlimited per side.
- Per-side target is `(target - barWeight) / 2`.
- Greedy load from heaviest to lightest.
- `achieved` is `barWeight + 2 * sum(platesPerSide)`.
- `remainder` is `target - achieved`.
- Exact means absolute remainder is at most `0.01`.
- Target below the bar reports `belowBar`, no plates, and a clear message.
- Target above 500 kg or below 0 is invalid input.
- Results display each plate group per side in descending order with counts.
- The calculator never updates a set automatically.

### 3.6 Unit behavior

- Existing canonical storage remains kg, km, and cm.
- Suggestion weights are stored in kg.
- Plate calculations use the current display unit and are not persisted.
- Height, weight, and plate labels use the existing `UnitConversionService` and formatters.
- No new storage key is introduced. Equipment is stored inside the profile and the plan.

## 10. ⚠️ Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The new onboarding step breaks existing route or step-count assumptions | High | Update flow, navigation, scaffold, and plan preview tests in SMART-05; run the full navigation suite |
| Legacy users lose equipment context | High | Default missing values to every group; never delete profile fields during load |
| Equipment selection produces unusably short days | Medium | Skip empty muscles with a warning and fill from allowed exercises; test bodyweight only |
| Suggestion logic surprises users or overrides intent | Medium | Do not overwrite completed history; show the reason; only prefill new uncompleted sets; keep zero when no history |
| Regeneration overwrites a user's moved days | Medium | Require an explicit Save and regenerate choice; keep Save only |
| lb increments and plate loadouts use wrong math | High | Keep the service unit-agnostic; test kg and lb tables separately; convert once at the coordinator boundary |
| Swap loses completed sets without warning | High | Require confirmation when any set is completed; cancel preserves state |
| Logger header becomes crowded | Medium | Use 32x32 icon buttons and test at 390x844 and 1.3x text scale |
| Exercise picker filtered to zero results | Medium | Fall back to all compatible exercises with a helper message |
| Existing plan output changes for full-gym users | Medium | Add a regression test that compares full-gym generation before and after |
| Scope grows into full periodization | Medium | Keep the algorithm deterministic and documented; defer RPE, deloads, and percentages |
| Plate sheet accepts invalid input | Low | Inline validation, max 500, bar comparison, disabled result |
